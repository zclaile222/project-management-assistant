# START-HERE：给负责安装这套工具的 Agent

你在读这份文件，说明有人要在一个新的地方用这套工具。这份文件写给**你**：按顺序做完，用户不需要懂这套工具的内部设计。

## 这是什么，为什么要装

这是一套帮用户做项目管理的工具：用一张表格记下所有任务和每一次进展，由助理按固定节奏（工作日早晚各一次，周六一次）提醒用户该处理什么。表格可以是在线的（飞书、钉钉、WPS 表格）或离线的 Excel 文件，任选其一。记录可以随时读出来，用于写日报、周报，或做项目盘点。

它要解决的问题：同时推进多件事时，最容易出的两类错误——某件事没人记得去跟，悄悄漏掉；该催的时候没催，或者催错了时间。这套工具靠固定的判断规则和一张可核查的台账，减少这两类遗漏。

它不做什么：不替用户做决定，不会自己改掉已有记录。它只在用户说话或定时运行时读表、按规则判断、写回用户确认过的内容。

## 安装顺序

1. **问用户：台账放在哪。** 四个选项：飞书、钉钉、WPS 表格、离线 Excel 文件。不要假设是飞书。
2. **只建一张表。** 这套工具的设计是单表：一张表里放全部任务和历史记录，不建第二张核对表、不建辅助表。表名用户自定。
3. **在这张表的第一行写死表头**（见下方"表结构"），一字不差：

   ```
   紧急程度 | 事项 | 详情 | 启动时间 | 计划完成时间 | 协同部门/责任人 | 推进状态（数字代表步骤） | 存在问题与协调（数字代表日期） | 任务编号 | 提醒开关 | 下次提醒日 | 今天应提醒
   ```

   如果用户要扩展（结束日期、重点、周期三列），在后面加：`结束日期 | 重点 | 周期`。扩展是可选的，不扩展也能正常使用。

4. **导入示例任务**（见下方"示例任务"），让用户先看到各种状态长什么样，再决定要不要删掉示例、换成自己的任务。
5. **填写运行配置**：把 `04-工具/运行配置.json` 里的占位符换成这张表的真实标识（表格 ID、工作表名等，具体取决于台账）。
6. **生成入口文本**：运行 `python 提醒工具.py 入口 chat`（以及 `morning`/`evening`/`weekly`），得到绑定了当前路径的完整入口文本，交给负责执行早晚周三场的助理或定时任务。
7. **提醒用户：真正的定时任务要在运行它的应用里自己设置。** 这个包能确保内容正确，不能替用户设置好闹钟式的调度。

## 台账原理（台账具体怎么操作，由你自行探索，本文件不规定）

工具只认一种"导出格式"（见 `提醒工具.py` 的 `payload()`、`page()`），不认台账来源。你的任务是让用户的台账能提供工具需要的数据，并保证写回时能原样写回。

下面三件事必须做到，这是底层原理：

1. **能读出整张表的当前内容**，并带上行号和版本标识。工具靠行号和版本确认读到的是同一份数据，读不全就不能发清单。
2. **能写入指定单元格，并回读确认写入结果。** 每次写入后都要读回来核对，不能只相信"写入成功"的返回值。
3. **A、B、I、J、K 五列的值正确、可读。** L 列（今天应提醒）由提醒工具根据这五列计算，不依赖台账自己的公式，也不要手填。

飞书是本项目唯一完整验证过的台账，其余台账的接口形态、下拉实现、日期格式都需要你自己核实。本文件不包含任何平台的连接命令或凭证，也不连接任何人的台账。

## 表结构：每一列是什么、什么格式、为什么这样设计

| 列 | 表头 | 填什么、什么格式 | 为什么这样设计 |
|---|---|---|---|
| A | 紧急程度 | 下拉：(待处理)、高优先、项目、跟进中、已传递、低优先（在办）；已完成、已取消、已转交结项、已归并（结束）。会根据任务的实际情况给出当前建议状态，但最终由用户确认，不会自动改动 | 区分在办、等待（已传递是在等别人，不算结束）、真正结束 |
| B | 事项 | 一句话概括这件事 | 不能留空，否则程序判断不出这是不是任务 |
| C | 详情 | 背景、范围、关联的其他任务（写对方编号） | 补充信息，程序不读 |
| D | 启动时间 | 开始做事的时间，可留空 | 与"什么时候提醒"是两件事 |
| E | 计划完成时间 | 就是截止日（deadline），`yyyy-mm-dd`，没有可留空 | 截止日和提醒日分开，才能做到"截止日很远但每天提醒我推进"或"还没定提醒日" |
| F | 协同部门/责任人 | 谁在做、谁在等 | 多线并行时一眼看出卡在谁手里 |
| G | 推进状态 | 把事情拆成几步，**当前要做的那一步写在最上面** | 判断"现在该做什么"的依据，要常更新 |
| H | 存在问题与协调 | **本工具最重要的一列**：任何时候有任何变动，都在这里写一条带日期的备注（格式 `M.D 内容`，最新的写最上面）。无论是推进、退步还是维持原状都要记，例如"6.3 今天未推进，等 XX 确认方案卡住"。一次更新不一定改变 A 列状态，但只要和这件事有关，就该记一条 | 保留完整历史，随时能回查这件事是怎么走到今天的 |
| I | 任务编号 | 唯一标签，形如 `前缀-0001`；前缀安装时自定，1–4 个英文字母。录入后不要改。之后可以直接说"XX-0012 推进到哪一步了"来更新它 | 行号会变，编号不会；编号是程序找到这一行唯一可靠的方式 |
| J | 提醒开关 | 下拉：开启 / 搁置 / 关闭。**开启时，这件事每次都会出现在提醒列表里**；搁置是明确先放一边、不主动催；关闭是不再提醒，但不等于做完 | 把"要不要催"和"做完没做完"分开，关闭不会被误当成完成 |
| K | 下次提醒日 | 给将来要处理的事设定一个开始提醒的日期，`yyyy-mm-dd`。到了这天才会出现在列表里 | 和 E 分开，因为两者常常不同 |
| L | 今天应提醒 | **由提醒工具计算，不要手填** | 覆盖所有判断：1=今天提醒，0=不提醒，搁置=搁置，待设置=漏填提醒日，待核实=编号或日期本身有问题 |
| M（可选） | 结束日期 | 整件事真正结束那天的日期，只在结项时填 | "本周完成了什么"要看事情真正结束的那天，不能从 H 里猜 |
| N（可选） | 重点 | 只填"是"或留空 | 用户亲手标的重点，只影响排列，不改变谁被提醒 |
| O（可选） | 周期 | 下拉：每工作日 / 每周 / 每两周 / 每月，或留空 | 周期提醒的"下一次是哪天"交给程序算，不交给模型记 |

两条贯穿全表的约定：

1. **E、K、M 的显示格式统一用 `yyyy-mm-dd`**，不要混用。程序读的是显示文字，没有年份的写法（比如"7月9日"）程序看不出是哪一年，无法判断是否过期。
2. **不要手改 L 列。** 手填会覆盖计算结果，导致提醒判断和实际不符。

## 示例任务

安装后应导入一组示例任务，覆盖各种状态，并且明确标注为示例、可以删除。示例内容由打包时附带的示例表提供。它应当至少包括：在办（不同状态）、等待（已传递）、四种结束状态、开启/搁置/关闭三种开关、有周期的任务、重点任务，以及一条故意的异常（用于证明异常会被看见，不会被吞掉）。

## 互动句式（部署完成后，可以直接告诉用户这样说）

| 你可以这样说 | 系统会做什么 |
|---|---|
| "新任务：XX，周五前要交" | 记为新任务；截止日记周五；提醒日先定在下一个工作日，每天出现，直到你说做完或放下 |
| "XX下周三再提醒我" | 只设提醒日为下周三，之前不催 |
| "XX先放一边" | 移入搁置：工作日只计数，周六逐条列出，不主动催 |
| "XX改到下周一" | 更新截止日；提醒日只有同时说了才改 |
| "XX部分做完了，剩下的是……" | 记入进展，剩余动作置顶；整件事仍未结束 |
| "XX做完了" | 标记完成，记结束日期，停止提醒 |
| "XX不做了，原因是……" | 标记取消，记原因，停止提醒，不计入完成 |
| "XX交给某某了，我不再跟" | 标记转交结项，本人跟进停止 |
| "XX这周是重点" | 标为重点，到期时排在清单最前 |
| "XX每周五发一次" | 设为周期事项，下次日期由工具算出，不由助理心算 |
| "XX还没好，先别催" | 撤回每天催办，只问一次何时再看 |
| "XX现在什么情况" | 只读查询，回答表里已有的记录，不改动任何内容 |

## 装完之后，怎么知道装对了

- 跑一次 `python 提醒工具.py 入口 chat`，确认没有报错，且输出里的路径指向这台机器、这个安装目录。
- 看一次示例任务生成的清单：应该能看到到日的事项、搁置的事项，以及至少一条"待设置"或"待核实"的异常示例。
- 确认 `04-工具/运行配置.json` 里已经没有任何 `<安装时填写>` 占位符。

## 遇到你不确定的情况，怎么办

这份文件没有覆盖的具体问题（某个台账的接口怎么调、某个格式怎么写），由你自己判断解决，不必等待额外的预设流程。**唯一不能绕开的边界**：规则文件（`01-规则/规则定稿.md`）定义的判断逻辑本身——比如"截止日不等于提醒日""L 列异常值的含义""搁置和漏填要分开"——这些不是实现细节，是业务规则，改动前要向用户确认，不要因为某个台账实现起来不方便就悄悄改规则的含义。
